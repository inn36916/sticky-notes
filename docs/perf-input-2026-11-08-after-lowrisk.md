## C.3 环境噪声归因：用「本轮未改动的路径」当标尺

`innerHtmlReadMs` 测的是**每键 `editor.innerHTML` 全量序列化**——这条路径本轮**完全没有改动**，
所以它的波动就是**机器状态的波动**，可以当作噪声标尺。

| 档 | 三轮 `innerHtmlReadMs` | max/min |
|---|---|---|
| S1 | 0.3 / 0.5 / 2.4 | 8.00× |
| S2 | 10.0 / 10.1 / 53.0 | 5.30× |
| **S3** | **28.7 / 65.2 / 74.8** | **2.61×** |

把 S3 的 `p50` 除以同轮 `read`（剔除机器状态影响）：

| 轮 | p50 | 同轮 read | **p50 / read** |
|---|---|---|---|
| 复测轮1 | 73.85 | 28.7 | **2.57** |
| 复测轮2 | 157.60 | 65.2 | **2.42** |
| 复测轮3 | 175.55 | 74.8 | **2.35** |
| 基线轮1 | 109.05 | 49.4 | **2.21** |
| 基线轮2 | 98.40 | 62.1 | **1.58** |

→ **三轮复测的归一化比值高度一致（2.35–2.57）**，说明 S3 每键成本里**可归因于实现的结构性部分没有变化**，
绝对值的起伏全部来自机器状态。**第 3 轮是明显的负载高峰**：同轮 S0 的 `flushMs` 从 7.1ms 涨到 20.0ms、
S1 从 6.4ms 涨到 25.8ms、S2 长任务从 1 个涨到 20 个。

**结论：每键延迟未改善，这与本轮范围完全一致**（每键成本 = 全量 DOM 序列化 + sendSync 全量拷贝，
治本方案「图片外置 + 小 patch 同步」不在本轮）。任何声称"本轮把每键延迟降下来了"的说法都是误读。

## C.5 落盘 `flushMs`（紧凑 JSON + 异步 worker）—— **未见改善**

| 档 | 基线轮1/轮2 | 复测轮1/轮2/轮3 |
|---|---|---|
| S0 | 5.7 / 4.8 | 7.1 / 6.4 / 20.0 |
| S1 | 7.1 / 6.6 | 9.8 / 5.9 / 25.8 |
| S2 | 27.5 / 24.8 | 30.9 / 23.1 / 62.7 |
| S3 | 78.7 / 67.7 | 73.3 / 92.1 / 87.7 |

→ **落盘耗时没有下降。** 原因：`flushMs` 测的是**主进程侧等待写盘完成的总时长**，
而改动后写盘已挪到 **worker 线程**——主进程不再被 `JSON.stringify` 阻塞，但 `flushMs` 仍要等到
worker 真正把字节写完才返回。**写盘本身的总 CPU/IO 没变，变的只是"不阻塞主线程"这件事**，
而这个收益**不出现在 `flushMs` 指标里**（它体现在"落盘在飞时按键是否排队"，见 C.6）。

**因此「紧凑 JSON + 异步 worker 降低落盘耗时」这个说法不成立**，准确表述是：
*把落盘从主线程挪走，使主线程在写盘期间仍可响应 IPC；磁盘写入本身的耗时基本不变。*

## C.6 落盘在飞时按键是否排队 —— **改善**

`updateIpcUnderFlushMs`（写盘在飞时的按键延迟）vs `updateIpcMs`（安静窗口）：

| 档 | 基线：安静 → 在飞 | 复测轮1：安静 → 在飞 | 比值（复测轮1） |
|---|---|---|---|
| S0 | 0.5 → 0.5 | 0.7 → 0.6 | 0.86× |
| S1 | 1.1 → 1.8 | 2.4 → 1.3 | 0.54× |
| S2 | 27.7 → 21.5 | 15.7 → 13.0 | 0.83× |
| S3 | 97.7 → 95.2 | 42.2 → 34.6 | 0.82× |

→ 基线里 S3 的"写盘在飞时按键"比"安静时"**还要慢**（97.7 vs 40.3），
改动后 **在飞时的按键不再比空闲时慢**（34.6 vs 42.2）——**落盘不再让按键排队**，这正是异步化的目标。

## C.8 复测结论（诚实版）

| 维度 | 是否改善 | 证据 |
|---|---|---|
| **每键延迟（95–134ms 量级）** | ❌ **未改善** | 归一化后 p50/read = 2.35–2.57，与基线 1.58–2.21 同量级；本轮不含治本方案 |
| **每次打字停顿的体感卡顿（4MB 真人节奏）** | ✅ **显著改善** | S2N 长任务 10 个 → 1 个 / 0 个；等效每键 100–102ms → **24.7–32.0ms** |
| **DOM 克隆次数** | ✅ **3 → 1** | e2e 运行时计数 |
| **落盘期间按键排队** | ✅ **消除** | S3 在飞时 34.6ms < 安静时 42.2ms |
| **落盘本身耗时** | ➖ **基本不变** | `flushMs` 与基线同量级；收益在"不阻塞主线程"，不在"写得更快" |

**一句话**：低风险三件做到了它该做到的事——**把"每次停顿"从一次明显的卡顿削掉了**，
但**没有、也不可能让"每个键"变快**；后者必须靠治本方案（图片外置 + 每键只同步小 patch）。

## C.9 本章数据的局限

1. **基线只有 2 轮，复测跑了 3 轮**，且复测第 3 轮落在明显的负载高峰（`innerHtmlReadMs` 涨到 74.8ms）。
   跨轮绝对值**不可直接相减**，必须看归一化比值。
2. **共享桌面、非独占环境**：同期多个常驻进程，绝对值只能给区间（复测 S3 p50 = **73.85–175.55**）。
   注意这个区间比基线（98.40–109.05）更宽，正是因为复测跨了一个负载高峰。
3. **`tailPathMs` 测的是旧路径**（脚本未改，逐行复刻 3 次克隆），它反映的是机器状态，不是新实现效果。
   新实现的直接证据是 e2e 的运行时 `cloneNode` 计数（= 1）。
4. **`flushMs` 不能证明"异步化提速"**，只能证明"写盘耗时没变"。异步化的收益在 C.6。
5. **未覆盖**：真实键盘与 IME、不同 DPI/缩放、最小化/完全遮挡、多便签争抢、非 Windows。
